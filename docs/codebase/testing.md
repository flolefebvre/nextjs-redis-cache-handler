# Testing

- The suite runs on Vitest 4, in three projects: `unit` (Docker-free, runs first), `integration` (needs Docker) and `e2e` (needs Docker, and the built output). Every script names its projects, so no run picks up a project by accident: `pnpm test` is `unit` and `integration`, `pnpm test:e2e` is `e2e` alone, last in the gate because it consumes what `build` produced.
- Tests are collocated with the file they test, as `.test.ts` files (`foo.test.ts` next to `foo.ts`). An integration test is named `.integration.test.ts`, which is what puts it in the `integration` project.
- Lay out each test body as Arrange / Act / Assert, one blank line between phases; two phases that fuse into one statement share a block, and a phase a test doesn't have is simply absent.
- The container harness lives in `tests/` (`global-setup.ts`, `redis-container.ts`); test files never wire it themselves. The integration global setup starts one server for the run and hands its URL to every worker: read it with `inject("redisUrl")`.
- Helpers a unit test shares with another live in `tests/unit-harness.ts`, the Docker-free counterpart of that harness: small, independent functions and types (an `Equals` type, the handler method names, an `entryOf()` Entry factory, a `stopwatch()`), never a framework a test has to be written around. An integration test takes one from there too when the helper needs nothing of Docker.
- `CACHE_TEST_IMAGE` runs the suite against another server image (the default is the single constant `DEFAULT_TEST_IMAGE` in `tests/redis-container.ts`); `CACHE_TEST_REDIS_URL` runs it against an already-running server and starts no container at all.
- A test that breaks the server starts one of its own, with `startOutageRedis` from the same harness: it needs Docker, so the outage tests are skipped when `CACHE_TEST_REDIS_URL` is set. The shared server of the run is never paused or stopped — every other worker is talking to it. A test that needs a whole deployment starts one the same way, with `startClusterRedis` or `startSentinelRedis` — one container each, one test file each, skipped under `CACHE_TEST_REDIS_URL` for the same reason — and the cells every injected client owes, whatever its kind, live in `tests/topology-harness.ts`, so a cell added there runs against both deployments.
- A test never holds a node-redis client at its concrete type (`RedisClientType`, `RedisSentinelType`, `RedisClusterType`), and never lets two of them meet in one inference position — one `each` table, one array, one shared variable: it states `CacheClient`, or the harness's `TopologyClient`, where the client is built. TypeScript otherwise takes the best common type of those generics and works out their variance against each other, which costs gigabytes of `tsc` heap on its own (#77).
- A duration a test measures comes from the monotonic clock, through `stopwatch()` in `tests/unit-harness.ts`, never from `Date.now()`: a host whose wall clock steps backwards mid-test — an NTP correction, a virtual machine resyncing — hands back an elapsed time short by the step, negative ones included. `Date.now()` stays where a test produces a _timestamp_, an Entry's among them.
- A Sentinel on a stepping host enters TILT — its own protection when its cron sees the wall clock go backwards or jump forward by more than two seconds — and suspends every failover action for thirty seconds, abandoning any failover in flight without publishing `+switch-master`. A cell that needs a failover therefore asks for one through `failedOver` in `tests/topology-harness.ts`, which waits the Sentinel out of TILT and asks again, and never waits a delay. The budget there is one TILT period, so a host that steps its clock repeatedly holds the Sentinel in TILT throughout and the cell skips itself with that reason: a skip there is the developer host's clock, not a regression, and CI — whose clock holds still — runs the cell.
- `tick()` is a pause on the app clock, and on a clock that is running it buys exactly one thing: the stamp that follows lands past the millisecond the one before it was stamped at — the Entry-before-event direction, which a tie already decides against the Entry anyway. It is never a margin in the other direction. The Handler clock is non-decreasing, so a backward step of the host's wall clock holds it at its floor and no wait moves it at all (ADR 0003): an Entry whose render started after a tag event stamped in the same hold is dropped, and a cell that waits for the gap goes red the moment it straddles one. A cell that needs an Entry to be later than a tag event therefore _moves_ the Handler clock on past that event, with `moveHandlerClockOn` and by more than the render length the Entry declares, and never waits for it.
- A hook a cell expects an event to fire is awaited, never asserted at an instant: the hook fires when the event lands, which no instant of the app clock names. `vi.waitUntil` is how a cell waits for one.
- A test asserts what a caller can observe — what `get` returns, what the server holds, which hooks fired, how long an operation took. No test inspects internal state, and none uses fake timers or a fake client.
- Every test uses a fresh random key prefix and cleans nothing up.

## The e2e project

- One Scenario per file, `e2e/<scenario>.e2e.test.ts`, files sequential: a Scenario is one narrative, and its steps read the Instances' output in order.
- The Fixture app under `e2e/fixture` is a workspace package that imports the library by package name, through the `exports` map, exactly as a consumer does. It is never imported from `src` or `dist`, and `next` is pinned there to the exact version the root devDependency names.
- Two `next build`s per run, in `e2e/global-setup.ts`, selected by `NEXT_CACHE_E2E_HANDLER`, which `next.config.ts` derives both the Handler slot modules and the `distDir` from, so the two outputs coexist and `next start` serves the one its Instances were started for. The `recording` build runs with the store reachable — its workers write their Entries under a build Key prefix, the prewarm every Scenario on that build starts from — and the `zero-config` build registers the library's Zero-config entry (`handlerPath`, and `require.resolve` of the `./handler` subpath for the `remote` slot) and runs with no `REDIS_URL` at all, which is what keeps a build box without a store buildable. It writes no Entry, so a Scenario on it is seeded from nothing. `distDirOf` in `e2e/fixture-build.ts` is the harness's single source for the `distDir`, mirrored by the one ternary in `next.config.ts`; everything that reads build output — the Server Action manifest among it — goes through it, since two builds mint two ids for one export.
- A Scenario file starts with `startInstances("<scenario>")` and needs nothing else: it mints a fresh Key prefix, seeds it from the prefix its build wrote under — with `SCAN` + `COPY` (Redis 6.2 / Valkey 7.2, the supported floor), asserting it copied something — when that build wrote one at all, then starts two Instances on random free ports. Two Scenario files therefore never see each other's Entries or revalidations.
- What a Scenario needs twice lives in the harness, never in a second Scenario: waiting a marker out until the scope that carries it has re-rendered or until two requests agree on it, and carrying back what a response set as cookies — Draft Mode's bypass cookie among them — are `instances.ts` (`markersOnceChanged`, `markersOnceStable`, `Page.cookies`, `cookieHeader`), and the Fixture's paths and the marker set each of its pages owes are `e2e/pages.ts`.
- What a Scenario changes about its Instances goes through the options of `startInstances`, never a second starter: `build` picks which of the run's builds they serve, `store: "none"` starts them with no `REDIS_URL` at all — not even an inherited one — `store: "own"` starts a server for that Scenario alone, and `env` adds the library's own `NEXT_REDIS_CACHE_*` variables, for a Scenario whose narrative is a configuration.
- The run's store is never paused nor stopped, in the e2e project as in the integration one: every other Scenario is talking to it. A Scenario that breaks a store asks for `store: "own"`, which has the harness start one with `startOutageRedis` and remove it with the Instances, and hands the pause back on the Instances themselves — `startInstances` overloads to `OwnStoreInstances`, so `instances.store.pause()` exists on that Scenario and on no other, and no Scenario reaches for the container harness. `COPY` never crosses two servers, so those Instances are seeded from nothing and warm what they need with their own first requests, as a Scenario on the Zero-config build does. They are skipped under `CACHE_TEST_REDIS_URL` — a provided server is nobody's to pause — through `canPauseStore()`.
- A step waits a log line out with `instances.logged(instance, text)` and asserts the absence of one with `instances.loggedSoFar(instance, text)`, which waits for nothing: the absence is read once the step has waited out something the same failure would have produced.
- A Scenario on the `zero-config` build has no recording wrapper in the path, so it Records nothing and no record file is created for it: it asserts on HTTP output and on what an Instance logged, through `instances.logged(instance, text)`, which waits the line out and never opens a log by a path it guessed.
- The harness is the only thing in `e2e/` that talks to Redis. A Scenario asserts what a user can observe — status, HTML, the `data-rendered-at` marker of every cached scope — and what the Fixture recorded, never a key.
- The Handler slot module of the `recording` build is a wrapper around the factory, configured with `optionsFromEnv` and writing one Recorded call per method invocation as a JSONL line — its `outcome`, and the `size` a `skip` event carries. A step takes `calls.end()` before it drives anything and reads `calls.since(offset)` after, so it sees its own calls and no one else's; work Next.js does in the background is awaited with `calls.waitFor(offset, …)`, never slept on.
- A step asserts the _set_ of `<method> <outcome>` pairs an Instance recorded, through `outcomesOf`, never their order: which cache scope is read first is Next.js's business.
- The Fixture carries one pages-router page with `runtime: 'experimental-edge'`. It is the permanent build guard for the Edge-bundle regression, and `e2e/build-output.e2e.test.ts` keeps the guard from going vacuous: the Edge chunks must carry the disabled handler and none of the Node.js target.
- Everything the run generates — the `.next*` build outputs, the record files, the Instance logs — lives under `e2e/fixture/` and is gitignored, and the `.next*` glob is what the format, lint and duplication checks skip, so a third build variant touches `distDirOf` and the `next.config.ts` ternary only.
