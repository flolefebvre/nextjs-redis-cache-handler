# CI

`.github/workflows/ci.yml` is three jobs on `ubuntu-latest` — `ci`, the gate, `e2e`, and `matrix`, the server matrix — run on every pull request and every push to `main`, and callable by a release workflow through `workflow_call` so the release path runs this exact gate. A superseded run on the same ref is cancelled, except on `main`, where every push keeps its run.

- Run the checks as one job step per `gate` script, in the gate's order, so a failing check names itself in the run summary.
- Pin `node-version` to the major the repo is developed on. `engines` only sets a floor (`>=22.12.0`), so a spec taken from it would let CI drift onto a major nobody has run.
- Keep `pnpm/action-setup` ahead of `actions/setup-node`, which needs pnpm on the PATH for `cache: pnpm`. The repo has no `packageManager` pin — a published library must not impose one on its consumers' toolchain — so the pnpm major is named in the workflow.
- The Test step needs the runner's Docker daemon: the `integration` project starts its own throwaway Valkey.
- The `e2e` job is separate, and runs on every pull request like the gate: it installs, runs `pnpm build` — the Fixture app consumes the built output through the `exports` map — and then `pnpm test:e2e`, which is also the gate's last step. Its budget is minutes rather than seconds, so it carries its own `timeout-minutes` (10, for a 2–4 minute run) and leaves the `ci` job's alone.
- The `matrix` job runs the `integration` project alone, once per supported server image, through `CACHE_TEST_IMAGE`: the floors the README declares (`redis:6.2`, `valkey/valkey:7.2`) and the latest of each family (`redis:8`, `valkey/valkey:9`). The floors are in the matrix, not only the latest: a command that exists on one server and not another — `EVALSHA_RO`, which node-redis emits for a script declared read-only and which Redis gained in 7.0, is the kind of case this job exists for, and why `src/script-runner.ts` declares every script a write — is otherwise only proven portable by a user report. `fail-fast: false`, so one unsupported command is one red cell and the other three still say what they know. The `unit` and `e2e` projects stay on the default image: they prove behaviour, not portability, and `unit` starts no server at all. `tests/server-version.integration.test.ts` asserts the running server is at or above its family's floor — `REDIS_VERSION_FLOOR` and `VALKEY_VERSION_FLOOR` in `tests/redis-container.ts` — so a mis-tagged image fails the cell instead of quietly proving nothing.

Before pushing a change to either workflow, lint it with `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest`, and reproduce CI's environment by running `pnpm gate`.

## Release

`.github/workflows/release.yml` runs on `v*` tags only, so landing a pull request never publishes. It is three stages: `guard` (the `NPM_TOKEN` secret is set, and the tag equals `package.json`'s version), then `ci` through `uses: ./.github/workflows/ci.yml` — the calling job stays in progress until all three of that workflow's jobs finish, so nothing is published on a green gate and a red `matrix` — then `publish`, which reinstalls from the committed lockfile, runs `npm publish --provenance --access public` (npm, not pnpm: `pnpm publish` has no `--provenance` flag) and cuts the GitHub Release with `gh release create --generate-notes --verify-tag`. `docs/releasing.md` is the maintainer's walkthrough, including the switch to npm trusted publishing after `0.1.0`.
